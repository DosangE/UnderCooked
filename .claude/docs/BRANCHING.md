# 브랜치 전략

이 저장소는 feature 브랜치 + PR 방식으로 작업한다. 구조 스타일은 ProtoHarness의
"CLAUDE.md는 간결하게, 세부 규칙은 문서 폴더에 두고 먼저 읽는다" 방식을 따른다.

---

## 1. 브랜치 3단 구조

```
dev_<작업명>   →  PR  →   dev   →  PR  →   main
   (작업 단위)      (통합/개발)      (최종/배포)
```

| 브랜치 | 역할 | 직접 커밋 |
|---|---|---|
| `main` | 최종 안정 버전. 배포·제출 기준점 | 금지. `dev` → `main` PR로만 반영 |
| `dev` | 통합 브랜치. 여러 작업이 여기로 모인다 | 금지. `dev_*` → `dev` PR로만 반영 |
| `dev_<작업명>` | 개별 작업 브랜치. 기능 하나, 실험 하나 단위 | 자유롭게 커밋 |

`main`과 `dev`에는 직접 push하지 않는다. 항상 PR을 거친다.

---

## 2. 작업 흐름

1. `dev`에서 새 작업 브랜치를 만든다.
   ```bash
   git checkout dev
   git pull origin dev
   git checkout -b dev_<작업명>
   ```
2. `dev_<작업명>`에서 작업하고 커밋한다. 이 브랜치는 자유롭게 여러 번 커밋해도 된다.
3. 작업이 끝나면 GitHub에 push하고 `dev_<작업명>` → `dev` PR을 연다.
   ```bash
   git push -u origin dev_<작업명>
   gh pr create --base dev --head dev_<작업명>
   ```
4. 리뷰(본인 리뷰 포함) 후 `dev`에 병합한다. 병합 후 작업 브랜치는 삭제한다.
5. `dev`에 변경 사항이 어느 정도 쌓이고 안정적으로 동작이 확인되면 `dev` → `main` PR을 연다.
   ```bash
   gh pr create --base main --head dev
   ```
6. `main`으로 병합되면 그 시점이 하나의 마일스톤(제출/발표 기준)이 된다.

---

## 3. 브랜치 이름 규칙

`dev_<작업명>` 형식. 작업명은 영문 kebab-case, 무엇을 하는지 한눈에 알 수 있게 짧게.

예:
- `dev_reward-shaping`
- `dev_curriculum-stage2`
- `dev_obs-refactor`
- `dev_bugfix-pot-timer`

버그 수정은 `dev_bugfix-<내용>`, 실험/튜닝은 `dev_exp-<내용>` 처럼 접두어로 구분해도 된다.

---

## 4. 커밋 메시지

한 줄 요약 + 필요하면 본문. "무엇을 왜 바꿨는지"를 남긴다. 예:

```
카운터 핑퐁 보상 어뷰징 차단

같은 카운터에 아이템을 놓았다 집었다 반복해서 보상을 누적하는
루프가 있어, 동일 아이템-카운터 쌍에 대해 쿨다운을 추가.
```

---

## 5. PR 규칙

- **`dev_*` → `dev` PR**: 이 작업이 무엇을 했는지, 어떻게 확인했는지 설명. 작은 단위로 자주 올린다.
- **`dev` → `main` PR**: 이번 마일스톤에 무엇이 쌓였는지 요약. 학습 결과·검증 결과가 있으면 같이 남긴다.
- 병합 후 원격의 작업 브랜치(`dev_*`)는 삭제한다. 로컬 브랜치도 정리한다.
  ```bash
  git branch -d dev_<작업명>
  git push origin --delete dev_<작업명>
  ```

---

## 6. 예외

- 오타·문서 수정처럼 아주 작은 변경도 원칙적으로는 `dev_*` 브랜치를 거친다. 다만 README 오타 등 사소한 것은
  본인 판단으로 `dev`에 직접 커밋해도 된다 (동작에 영향 없는 것만).
- `main`에는 항상 PR로만 들어간다. 예외 없음.
