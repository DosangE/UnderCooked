# UnderCooked 최종 산출물 검증

검증일: 2026-10-07. 대상: 작업 시작 시 `dev`, 커밋 `87ded4e`.

**판정: 핵심 성공률은 보관된 원자료에서 재현된다. 협동 요리 환경이라는 목적에도 부합한다. 그러나 보고서 전체가 정확하다고 승인할 수는 없다. 최종 모델의 설명, 평가 실행 방식, 보상 설정, 선택 비율 계산, 일부 단정적인 해석에 수정이 필요하다.**

고의로 결과를 조작했다는 증거는 발견하지 못했다. 이 검증은 저장소 내부의 일관성과 원자료 재집계에 대한 것이며, 원자료 생성 과정 전체의 진위나 새로운 실행에서의 성능을 인증하지 않는다.

## 1. 범위와 방법

- README, 설계 기록, 날짜별 결과 보고서, 카페 게시용 DOCX의 본문 및 표, DOCX 생성 스크립트를 대조했다.
- 현재 C# 환경 코드, 프리팹과 씬, YAML 설정, 보관된 학습 설정, ONNX 그래프 메타데이터를 확인했다.
- TensorBoard 이벤트가 있는 46개 런 폴더, 에피소드 로그 5개, 냄비 채움 로그 8개를 다시 읽었다. 기존 `summary.txt`를 근거로 수치를 복사하지 않았다.
- 제출 모델과 보관 모델의 SHA-256을 비교했다. ONNX 입력·출력 및 LSTM 노드 존재를 읽었으며 모델 추론은 수행하지 않았다.
- Git에 남아 있는 별도 Memory 실험 브랜치의 보고서를 읽었다. 브랜치를 전환하거나 병합하지 않았다.
- Unity 에디터에서는 실행·회귀 검사·재평가를 하지 않았다. 사용자가 현재 다른 프로젝트를 열어 두었다고 알려온 뒤 Unity 도구 사용을 중단했다. 그 에디터의 상태나 콘솔을 이 프로젝트의 검증 근거로 사용하지 않았다.

검증용 스크립트: `tools/verify_results.py`. 재집계 결과와 원자료 해시: `reports/2026-10-07-audit-evidence.json`.

실행 예:

```powershell

```

스크립트는 `tensorboard`가 필요하며 Unity를 실행하지 않는다. 입력 결과 파일을 변경하지 않고 검증 JSON만 쓴다. DOCX 내용은 별도로 번들 Python의 `python-docx`로 읽었다. DOCX 페이지 렌더링은 LibreOffice 실행 파일이 없어 완료하지 못했다. 따라서 페이지 잘림·배치·인쇄 상태는 승인하지 않는다.

## 3. 우선 수정할 문제

### 3.1 최종 보고서가 현재 제출 모델을 잘못 식별한다

**중요도: 높음. 확정된 문서 불일치.**

`reports/2026-09-29-final-report.md:26`과 `:246`은 현재 `models/undercooked.onnx`를 `undercooked_final3`로 설명한다. 실제 파일은 145차원 `undercooked_blue_urgent3`다. 그 보고서의 재료 2종 성적 자체는 맞지만 현재 제출 파일에 연결한 설명은 틀리다. README 끝에서도 이 파일을 단순히 “최종 보고서”로 안내한다.

해당 문서는 재료 2종 단계의 역사적 보고서임을 명시하고 모델 경로를 `archive/runs/undercooked_final3/Chef.onnx`로 바꿔야 한다. 현재 최종 결과는 10-04 확장 보고서로 연결해야 한다. 오래된 보고서의 재현 명령도 당시 코드 기준임을 표시해야 한다. 현재 `StageCurriculum`은 6종까지 가는 수정된 단계표이므로 과거 재료 2종 실험을 현재 코드로 그대로 재현할 수 없다.

### 3.2 기록된 99.5%를 Unity 내부 ONNX 직접 추론 성적으로 간주할 수 없다

**중요도: 높음. 평가 실행 방식과 주장 범위를 구분해야 한다.**

`reports/2026-10-04-blue-ingredient.md:222`와 평가 YAML 머리말은 `mlagents-learn --inference --initialize-from=...`로 평가했다고 명시한다. `episode_log_public.cs` 역시 트레이너가 에이전트를 제어하는 상태에서 기록한다. 프리팹의 Behavior Type은 Default다.

로컬 ML-Agents 패키지 `Runtime/Policies/BehaviorParameters.cs:248`에서는 Default이고 communicator가 연결돼 있으면 `RemotePolicy`를 선택한다. 이 방식은 Python 정책으로 Unity 환경을 제어하는 평가이며 Unity의 ONNX/Sentis 직접 추론과 다르다. 공식 [BehaviorParameters 구현](https://raw.githubusercontent.com/Unity-Technologies/ml-agents/release_22/com.unity.ml-agents/Runtime/Policies/BehaviorParameters.cs)도 같은 분기를 보여 준다.

따라서 **기록된 정책 평가 성공률 99.5%는 유효하지만, 현재 ONNX의 Unity 내부 직접 추론 성공률 99.5%까지 검증된 것은 아니다.** “Unity 환경에서 Python 정책을 학습 없이 평가”로 표현을 정확하게 바꾸거나, 현재 모델로 트레이너 없는 평가 결과를 별도로 보관해야 한다. 재료 2종 모델의 과거 ONNX 점검 스크립트는 있으나 이것이 현재 6종 모델의 직접 추론 성적을 대신하지 않는다.

### 3.3 Word의 최종 보상 표가 마지막 학습 조건과 다르다

**중요도: 높음. 확정된 설명 오류.**

`posts/2026-10-04-cafe/최종 프로젝트 - UnderCooked.docx` 본문 문단 66과 표 3은 “최종 보상 구성”이라면서 만료 벌점을 −0.5로 적고 급한 주문 보너스를 생략한다. 그러나 최종 학습의 실제 `archive/runs/undercooked_blue_urgent3/configuration.yaml`은 **90초 / 목표 8 / 주문 30초 / 만료 −3 / 급한 주문 보너스 +3 / γ 0.995**다.

45초 평가에서는 평가 설정에 보너스가 없어서 기본값 0이고 만료 벌점은 −0.5다. Word의 기본 보상 표를 유지하려면 평가·기본 환경의 보상이라고 표시하고 마지막 학습 조건을 별도로 적어야 한다. “개인 보상은 행동한 셰프만 받는다”도 전달 보상에는 맞지 않는다. `ChefAgent`는 전달을 성사시킨 두 셰프에게 각각 +0.15를 지급한다. 생성 원본 `make_post.js:154` 이후도 함께 정정해야 한다.

### 3.4 요리별 선택 비율 계산에 분자·분모 불일치가 있다

**중요도: 높음. 실제 분석 코드 오류.**

`archive/tools/analyze_pot_fills.py:52`는 **첫 재료 투입 시점의 주문**을 분모로 센다. `:53`은 **두 번째 재료 투입 시점에 맞게 만들어진 모든 냄비**를 분자로 센다. 두 투입 사이에 새로 등장한 주문도 분자에 들어가므로 분자가 분모 사건의 부분집합이 아니다. 그림 생성기 `archive/tools/figures/plot_blue.py`도 같은 계산을 사용한다.

실제 `eval_blue_final`의 GreenSoup은 799/740 = **107.9730%**다. 첫 투입 시 그 요리가 주문판에 있던 경우에만 분자를 세면 725/740 = **97.9730%**다. 이 런에는 첫 주문판에 없던 요리를 나중 주문판과 맞게 만든 기록 93개가 있다. 예를 들어 `archive/runs/eval_blue_final/fills.csv:34`의 첫 주문판에는 MixSoup이 없지만, 두 번째 투입 때 새 MixSoup 주문이 생겨 맞게 만든 것으로 집계된다.

현재 최종 모델의 RedSoup 16.6%, RedBlueSoup 12.6%는 이 오류의 영향을 받지 않는다. GreenSoup만 921/1021 = 90.2057%에서 **920/1021 = 90.1077%**로 바뀐다. 따라서 최종 성공률을 무효화하는 오류는 아니지만, “첫 주문판에 있을 때 선택한 비율”이라는 정의와 분석 도구를 고쳐야 한다. 해당 비율은 주문 티켓의 처리율이나 서빙 성공률도 아니다.

### 3.5 LSTM 사용과 LSTM 필요성 입증을 혼동한다

**중요도: 중간. 효과가 확인되지 않은 설계 의도를 단정한다.**

Word 문단 48과 `make_post.js:124`는 “기억(LSTM)이 필요한 문제로 만들었다”고 한다. 현재 코드에서 조리 완료 상태를 직접 관측하거나 마스크로 노출하지 않는 것은 맞다. 하지만 반복해서 떠보기와 다른 관측의 시간 단서로도 해결할 수 있으므로 이것이 LSTM의 필요성 증명은 아니다.

별도 브랜치 `origin/dev_exp-memory-ablation`, 커밋 `d23787b`의 `reports/2026-09-26-memory-ablation.md`는 해당 실험에서 Memory on/off 모두 성공했고, 효과를 확인하지 못했다고 명시한다. 쉬운 재료 2종 이전 조건의 단일 런 비교이므로 현재 6종에서 Memory가 무효라고 결론내릴 수도 없다.

정확한 표현은 **“조리 완료를 숨기고 LSTM을 사용했다. 현재 최종 6종 조건에서 LSTM의 필요성·성능 개선은 검증하지 않았다.”**다. 주문 관측을 없애면 반드시 한 요리만 만든다는 설명도 ablation을 하지 않았으므로 설계상 예상으로 표시해야 한다.

## 4. 추가로 정정할 수치와 해석

### 4.1 파랑을 한 번도 쓰지 않았다는 설명은 원자료와 다르다

`reports/2026-10-04-blue-ingredient.md:123`은 blue_final에서 파랑이 냄비에 한 번도 들어가지 않았다고 한다. 그러나 `eval_blue_final/fills.csv:2115`에는 첫 초록, 두 번째 파랑으로 GreenBlueSoup을 맞게 만든 기록이 **1회** 있다. 같은 보고서 표에도 GreenBlueSoup 1회가 적혀 있다.

“파랑을 첫 재료로 선택한 경우는 0회이며, 파랑을 사용한 완성 냄비는 1회로 사실상 사용하지 않았다”가 정확하다. 초기 `blue_s1`의 학습 지표에서 사용 0회라는 주장과 `blue_final` 평가 결과를 분리해야 한다.

### 4.2 매 판 일부 주문은 반드시 만료된다는 설명은 틀리다

확장 보고서 `:158`, Word 문단 95 및 생성기 `:206`은 일부 주문의 만료가 매 판 불가피하다고 설명한다. 그런데 최종 에피소드 로그 **1105판 중 775판**은 25초 전에 목표를 달성했고 기록된 주문 만료도 0이다. 성공하면 바로 판이 끝나므로 남은 주문을 모두 처리할 필요도 없다.

문제의 정확한 설명은 **모든 주문을 처리하기 전에 목표를 채우고 종료해도 성공하므로, 일부 레시피의 주문을 피하는 정책도 높은 성공률을 낼 수 있다**는 것이다. 미처리 주문, 실제 만료 주문, 성공 종료 때 사라지는 주문은 서로 다르다.

### 4.3 기다려도 급한 주문 보너스를 유리하게 만들 수 없다는 보장은 없다

확장 보고서 `:184`와 Word 문단 112는 모든 주문의 시간이 같이 줄어드니 기다림에 이득이 없다고 한다. 이는 **주문이 만료·소진·교체되지 않는 동안에만 순위가 유지된다**는 설명이다. `OrderBoard.Tick`은 만료된 슬롯을 새 주문으로 채우므로 대기 중인 요리의 순위가 바뀔 수 있다.

코드상 반례: RedSoup 1초, GreenSoup 5초, BlueSoup 10초가 남아 있고 GreenSoup을 들고 있을 때 즉시 내면 가장 급한 주문이 아니다. 1.1초 기다려 RedSoup 주문이 만료되어 25초짜리 새 주문으로 교체되면 GreenSoup이 가장 급해져 보너스 대상이 된다. 만료 비용과 스텝 비용까지 포함한 전체 수익이 늘어나는지는 별도 비교가 필요하다. **현재 정책이 이 경로를 이용했다는 증거는 없지만 “순위만 보므로 기다림이 안전하다”는 논증은 충분하지 않다.**

### 4.4 일부 표의 평균 구간과 숫자가 맞지 않는다

TensorBoard 요약값의 단순 평균을 재계산했다. 이 평균은 판별 로그의 성공/판 수와 가중 방식이 다르므로 같아야 하는 것은 아니다. 다만 같은 구간·같은 방식이라고 적은 표는 재현돼야 한다.

| 대상 | 문서 값 | 재계산 | 필요한 정정 |
|---|---:|---:|---|
| urgent3 학습 마지막 0.5M | 99.0% (`blue-ingredient.md:97`) | 98.6013% | 98.6% 또는 집계 방식을 명시 |
| urgent3 45초 평가, 0 < step ≤ 600k 요약 평균 | 99.4% | 99.4793% | 한 자리 반올림이면 99.5%. 다른 구간을 썼다면 근거 명시 |
| urgent3 90초 평가, 전체 600k 요약 평균 | 98.9% | 99.0581% | 전체면 99.1%; 마지막 500k의 98.8697%를 썼다면 그 구간 명시 |
| blue_s1 종료 결과 | 약 45% | 마지막 0.5M 50.1980% | 45%가 나온 시점·구간을 명시 |
| lesson0 종료 결과 | 99.7% | 마지막 100k 99.7297%, 마지막 500k 97.6178% | 99.7% 자체는 맞지만 창 크기를 명시 |

또한 평가 이벤트 파일의 마지막 기록은 `urgent3_45` 620k, `urgent3_episodes` 740k, `eval_stage_s2_ft` 740k다. YAML의 `max_steps:600000`만으로 실제 추론 수집 종료를 확정할 수 없다. 에피소드 로그에는 수집 스텝과 주방 ID가 없어서 **1105판 로그의 정확한 수집 시작·종료 스텝을 판별할 수 없다.** 성공/실패 개수는 재현되지만 “모두 정확히 동일한 600k 구간”이라는 비교에는 추가 메타데이터가 필요하다.

### 4.5 할인 설명과 인과관계가 과도하게 단정되어 있다

γ 0.99에서 100~300 결정 뒤의 할인은 약 0.366~0.049이므로 문서의 계산은 맞다. 그러나 실제 long8_g995와 urgent 계열의 γ는 **0.995**다. 이 경우 같은 지연의 할인은 **0.606~0.222**다. 0.99의 숫자만으로 γ를 바꾼 실험까지 설명하면 조건이 어긋난다.

보너스 도입·증가, 추가 학습, 학습률 재시작을 분리한 대조가 없으므로 “보너스만이 편향을 바꿨다”, “늦은 벌점은 습관을 바꾸지 못한다”는 일반 명제는 입증되지 않았다. 이번 런에서 관찰한 변화와 가능한 해석으로 제한해야 한다. 마찬가지로 6종 모델이 2종보다 성공률이 높은 것은 학습 예산·정책·관측이 다른 결과이며 요리 종류 증가 자체의 개선 효과를 뜻하지 않는다.

### 4.6 87.5%와 재현성의 적용 범위를 명시해야 한다

87.5%는 6종 주문에서 초록 포함 3종을 각 슬롯이 독립·균등하게 뽑는다고 가정한 `1 - (1/2)^3`이다. 초기 주문 생성에는 들어맞는 계산이다. 하지만 플레이 도중에는 정책이 처리한 주문만 교체되므로 남은 주문판 분포가 달라진다. 최종 냄비 채움 로그에서 실제 첫 투입 시 초록 요리가 하나 이상 있었던 비율은 **82.0959%**다. 87.5%를 플레이 중 실측 확률로 표현하면 안 된다.

같은 시드의 벌점 대조에서 기록된 스칼라가 같은 사실은 확인했다. 시드 1은 공통 226지점, 시드 3은 공통 104지점에서 비교한 네 지표가 정확히 같았다. 그러나 이것만으로 모든 설정·하드웨어·버전·학습 체인이 비트 단위로 재현된다고 보장할 수 없다. 문서의 “같은 시드면 비트 단위 재현”은 해당 조건·관측한 스칼라의 범위로 좁혀야 한다.

### 4.7 MA-POCA 설명을 기술적으로 정확하게 고쳐야 한다

Word 문단 54의 “내가 없었다면”은 에이전트를 제거한 실험을 기준으로 기여도를 계산한다는 오해를 준다. MA-POCA의 counterfactual baseline은 해당 에이전트의 **관측은 유지하고 행동을 주변화**하며, 다른 에이전트의 관측·행동에 조건부인 기준값을 학습한다. “내 행동 대신 다른 행동을 했을 경우와 비교하는 기준값”으로 설명하는 편이 정확하다. [MA-POCA 원 논문의 Counterfactual Baseline 절](https://arxiv.org/html/2111.05992v2).

카페 글의 Overcooked-AI 비교는 **2019년 공개 논문의 설정**으로 한정하면 양파 수프 단일 레시피 설명이 맞다. 최신 환경 전체가 단일 레시피라고 일반화하지 않아야 한다. [2019년 논문 환경 설명](https://arxiv.org/html/1910.05789).

## 5. 프로젝트 목적과의 부합 여부

**협동 서빙은 부합한다.** `KitchenEnv`의 구역 제한과 스테이션 배치상 A만 냄비에 접근하고 B만 그릇함·서빙구에 접근할 수 있다. 성공하려면 빈 그릇과 완성 요리가 반드시 경계 카운터를 건너야 한다. `TryInteract`는 실제 대기 주문과 일치할 때만 서빙 수를 늘리며 `KitchenGroup`의 성공 종료 조건도 그 서빙 수다. 확인된 성공률은 단순 보상 증가를 성과로 잘못 읽은 것이 아니다.

**주문에 따른 요리 선택도 상당 부분 구현·학습되었다.** 주문 3슬롯이 관측에 들어가고, 최종 기록에는 여섯 요리의 정상 완성 냄비가 모두 존재한다. 그러나 RedSoup 16.6% / RedBlueSoup 12.6%와 GreenSoup 약 90%의 편향이 남는다. **99.5%는 3접시 목표 달성률이며 전체 주문 처리율, 요리별 동일 숙련도, 공정한 주문 선택을 의미하지 않는다.**

**상황마다 역할을 유연하게 다시 나누는 능력은 입증되지 않았다.** 물리적으로 강제된 운반 역할과 B가 재료 준비를 더 맡는 패턴은 보인다. 파트너·배치·역할이 바뀔 때의 적응이나 다른 정책과의 협동은 평가하지 않았다.

MA-POCA, 행동 마스킹, LSTM, 커리큘럼을 사용한 구현 근거는 있다. 이것은 각 개념의 추가 성능 효과를 독립적으로 증명한 것과 다르다. 공식 과제 원문 `최종_프로젝트.md`는 현재 검증 대상 파일에서 확인하지 못했으므로, 제출 체크리스트만으로 채점 기준 전체 충족을 인증하지 않는다.

## 6. 증거의 한계와 권장 정정 순서

- 서빙 수는 공개 로깅 코드가 완료한 에피소드의 마지막 서빙 수를 읽지만, 잘못 채움·잘못 제출·소요 시간 일부는 리셋 직전 에디터 프레임을 읽는다. 마지막 프레임의 이벤트를 놓칠 수 있다.
- 6종 에피소드 로거의 만료 수는 슬롯 타이머 변화로 추정한다. 마지막 0.6초에 정상 서빙한 주문을 만료로 오분류할 가능성이 코드 주석에도 명시돼 있다. “실패 6판 모두 주문 3개 만료”는 기록상 재현되지만 정확한 환경 이벤트 카운터로 독립 확인된 것은 아니다.
- 선택 비율 진단은 첫·두 번째 재료를 모두 식별한 완료 냄비만 사용한다. 버린 중간 냄비, 미완료 냄비, 식별하지 못한 기록은 분모에서 제외된다. 선택 순간 전체의 비율로 확대하면 안 된다.
- 99.4570%의 이항 Wilson 95% 구간은 98.8204~99.7509%다. 이는 독립 판이라는 가정하의 표본 오차 참고값이며 시드·학습 체인·버전 차이까지 포함하지 않는다.
- `KitchenSelfTest.RunAll`에서 17개 검사 호출을 확인했지만 이번 검증에서는 실행하지 않았다. 기존 “전부 통과” 기록을 현재 실행 결과처럼 승인하지 않는다.
- GIF의 마지막 성공 표시는 제작 스크립트에서 기록된 종료 서빙 수를 덧붙일 수 있게 되어 있다. 과거 보고서에 해당 제작 방법이 공개돼 있어 이를 조작 증거로 판단하지 않지만, 프레임 원본과 녹화 메타데이터 없이 특정 GIF의 시간·종료 장면을 독립 인증하지 않는다.

원본 코드·보고서·모델·평가 로그는 수정하지 않았다. 이번에 추가한 것은 검증 스크립트, 재집계 JSON, 이 검증 보고서다.

정정은 (1) 현재 최종 모델 및 평가 방식 명시, (2) Word 보상 표와 LSTM 표현 수정, (3) 선택 비율 분석 도구 수정 및 관련 표·그림 재집계, (4) 평균 구간 통일, (5) 만료·대기·할인·재현성에 관한 단정 축소 순으로 진행하면 된다. ONNX 직접 추론 성적 확인은 이 문서·코드 검증으로 대신할 수 없는 별도 실행 작업이다.
