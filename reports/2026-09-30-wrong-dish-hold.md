# 틀린 요리 보유 벌점 (2026-09-30)

## 요약

**틀린 요리를 버리는 행동은 늘었지만(+59%), 전체 성공률은 오르지 않았다 (95.5% → 94.3%, 오차 범위 안).**
한 번 실수한 판의 만회는 좋아졌지만(85% → 94%), 버리고 다시 만들다 또 틀리는 판이 두 배 넘게 늘었다.
남은 실패의 뿌리는 "실수 후 대처"가 아니라 "레시피를 고르는 정확도"다.

## 1. 왜

실패 분석(`reports/2026-09-29-experiment-results.md` §2-2c)에서 실패는 거의 전부 주문에 없는 레시피로 냄비를 채운 판이었고,
한 번에 학습한 정책(`undercooked_stage_s2`)은 틀린 요리를 버리지 않고 들고 버텼다.
지금 보상으로는 틀린 요리를 버리면(서빙구에 내면) 즉시 −0.5, 들고 있으면 0이라 "들고 기다리기"가 당장 싸다.

## 2. 무엇을 바꿨나

yaml 파라미터 `wrong_dish_hold_penalty`(초당, 음수)를 추가했다. **기본값 0 = 꺼짐**이라 기존 설정과 최종 모델의 학습 조건은 그대로다.

| 항목 | 내용 |
|---|---|
| 대상 | 어떤 대기 주문도 원하지 않는 요리. 셰프 손, 카운터, 조리가 확정된 냄비를 모두 센다 (`KitchenEnv.WrongDishesInPlay`) |
| 보상 | 요리 개수 × 초 × 벌점을 **팀 보상**으로 (`KitchenGroup.FixedUpdate`) |
| 버리면 | 즉시 멈춘다. 쌓인 벌점은 **돌려주지 않는다** |
| 진단 | `Kitchen/WrongDishSeconds` (벌점이 꺼져 있어도 기록) |
| 회귀 검사 | [14] 손 / 카운터 / 확정 냄비 / 두 개면 2배 / 맞는 요리는 0 / 버리면 멈춤 / 기본값 꺼짐. 14개 항목 전부 통과 |

설계에서 정한 것:

- **손에만 붙이지 않았다.** 카운터에 내려놓아 피하는 것을 배우기 때문이다.
- **냄비는 조리 확정(`IsCommitted`)만 본다.** 조리 완료(`HasCookedDish`)를 쓰면 관측에서 일부러 뺀 완료 여부가 보상으로 샌다.
- **환급하지 않는다.** 처음에는 "버리면 쌓인 벌점을 돌려준다"로 제안했는데, 그러면 20초 들고 있다 버려도 바로 버린 것과 비용이 같아
  빨리 버릴 이유가 없어진다. 구현 전에 바꿨다.
- 잘못 채울 때의 벌점(−0.3)과 틀린 요리 제출(−0.5)은 그대로 둔다. 만드는 순간 이미 손해라서 악용 경로가 생기지 않는다.

## 3. 실험

`configs/undercooked_final_hold.yaml` = `undercooked_final_pen03.yaml` + `wrong_dish_hold_penalty: -0.02`.
벌점 크기: 끝까지 쥐고 버티는 비용이 버리는 비용(0.5)보다 커지도록, 25초면 −0.5.

| 런 | 출발점 | 시드 | 스텝 | 다른 점 |
|---|---|---|---|---|
| `undercooked_stage_s2_ft` (기준선, 09-30 이전) | `undercooked_stage_s2` | 2 | 3M | 없음 |
| `undercooked_stage_s2_hold` | `undercooked_stage_s2` | 2 | 3M (37.1분) | 보유 벌점 −0.02/s |

두 모델을 트레이너 `--inference`로 최종 난이도 600k 스텝씩 돌려 에피소드마다 기록했다 (`archive/tools/inference/episode_log.cs`).
기준선도 새 코드로 다시 돌렸다(`eval_stage_s2_ft_v2`). `Kitchen/WrongDishSeconds`가 새 코드에만 있어서다.
결과는 09-30 오전 측정(`eval_stage_s2_ft`, 95.6%, 잘못 채운 판 80.2%)과 거의 같게 재현됐다.

## 5. 해석

- **행동은 의도대로 바뀌었다.** 잘못 채운 판에서 틀린 요리를 버리는 횟수가 0.46 → 0.73으로 늘었고,
  한 번만 실수한 판은 93.6%로 만회한다 (기준선 85.4%).
- **하지만 버리고 다시 만들다 또 틀린다.** 잘못 채움이 2회 이상인 판이 34 → 85판으로 늘었다. 레시피를 고르는 정확도는 그대로라
  다시 만드는 횟수가 늘면 틀리는 횟수도 는다. 결과적으로 잘못 채운 판 전체의 성공률과 틀린 요리가 있었던 시간은 그대로다.
- **벌점이 작다.** 잘못 채운 판에서 벌점 합계는 약 −0.31 (15.7초 × 0.02). 서빙 +3, 목표 +2에 비해 작다.
- **뿌리는 레시피 선택이다.** 판의 22%에서 레시피를 틀리게 고르는 비율은 두 모델이 같다. 이 벌점은 그 비율을 건드리지 않는다.
- 런 1개, 3M뿐이다. 성공률 차이(−1.2%p)는 오차 범위 안이다.

## 6. 다음에 할 것 (하지 않음)

- **레시피 선택 쪽을 직접 겨냥한다.** 예: 냄비에 첫 재료를 넣을 때, 대기 주문 중 가장 급한 것과 맞는지로 작은 신호.
  다만 첫 재료는 여러 주문에 걸쳐 있을 수 있어(초록은 GreenSoup, MixSoup 둘 다) 설계가 필요하다.
- 보유 벌점을 키우는 것(예: −0.05/s)은 버리기를 더 늘리겠지만, 다시 틀리는 판도 같이 늘 가능성이 크다.
- 최종 모델(`undercooked_final3`)은 그대로 둔다.
