# Memory on/off 비교 실험 (2026-09-26)

README §3 ①(Memory / RNN)의 근거를 확인하려고, 조리 완료를 똑같이 숨긴 조건에서
memory를 켠 런과 끈 런을 처음부터 학습해 비교했다.

기준 커밋: `dev_exp-memory-ablation` `75aa612` (`dev` `66ebc13` + 헛도리 지표)
환경: 데스크탑 RTX 2080 SUPER, torch 2.2.2+cu121, mlagents 1.2.0.dev0, Unity 6000.3.18f1

---

## 1. 요약

- **이 조건에서는 memory가 도움이 되지 않았다.** memory를 끈 런이 첫 서빙은 0.6M, 목표 달성 99%
  도달은 약 1.5M 스텝 빨랐다. 둘 다 결국 100%에 도달했고, 에피소드 길이는 끈 쪽이 더 짧다.
- **헛도리(`Kitchen/PotNotReady`)는 두 런이 비슷하다.** 둘 다 100%에 도달한 뒤에도 에피소드당
  2~3회 덜 끓은 냄비를 뜬다. memory를 켠 정책도 "재료를 언제 다 넣었는가"를 기억해서 맞추는
  대신 냄비 앞에서 반복해서 떠보는 방식으로 풀었다.
- 결론: **조리 완료를 관측·마스크에서 숨긴 설계만으로는 기억이 강제되지 않는다.** 이유 후보는
  §5에 있다 (헛도리 벌점이 싸다, 관측에 시계 역할을 하는 값이 있다).

## 2. 설계

| 항목 | 값 |
|---|---|
| 난이도 | lesson0에서 `cook_time`만 2 → 5. `target_dishes 1, recipe_pool_size 1, needs_prep 0, cook_time 5, order_slots 1, order_duration 25, max_ingredients 2` |
| 초기화 | 두 런 모두 무작위 초기화 (memory 유무로 네트워크 구조가 달라 `--initialize-from` 불가) |
| 스텝 | 각 4M |
| 설정 | `configs/undercooked_ablation_mem_on.yaml` / `configs/undercooked_ablation_mem_off.yaml`. `network_settings.memory` 블록(`sequence_length 64`, `memory_size 128`) 유무만 다르다 (`diff`로 확인) |
| run-id | `undercooked_mem_on` (53분), `undercooked_mem_off` (43분) |
| 시드 | 각 1개 |

조리 5초는 약 50 decision이다 (에피소드 45초 = 449 decision).

### 추가한 진단 지표

`Kitchen/PotNotReady`: 조리가 끝나기 전에 빈 그릇으로 냄비를 뜨려 한 횟수(헛도리, 개인 −0.02).
보상과 무관한 순수 관측이다. 회귀 검사 [11]이 "조리 중에 뜨면 1회, 다 끓은 뒤 뜨면 그대로 1회,
요리가 담김"을 확인한다. 두 런 모두 실행 전 회귀 검사 12개 항목([1]~[11], [5b]) 통과,
`학습 모드 (트레이너 연결됨, 주방 16개)` 확인 후 진행했다.

진행 시점이 달라서, 같은 구간끼리 비교하면 memory 효과와 학습 속도 차이가 섞인다.

## 4. 곡선 요약

- **mem_off가 체인을 먼저 배운다.** 0.5–1.0M에 이미 냄비 확정 1회, 요리→B 0.22회였다.
  mem_on은 같은 단계에 2.5M쯤 도달했다.
- **mem_on은 2.0–2.5M에 정체했다.** 냄비 확정 약 1회에서 뜨기 0.25회로 멈췄고, 필요 없이 그릇을
  넘기는 횟수(그릇→A)가 5.35회까지 늘었다. 2.7M부터 서빙이 트이면서 한꺼번에 풀렸다.
- **헛도리는 두 런 모두 서빙이 트일 때 같이 늘었다.** 뜨기를 배우면서 조리 중에도 떠보는 시도가
  생긴 것이다. 그 뒤로도 줄지 않았다. mem_off는 2.5–3.0M에 3.1회로 최대, 이후 2.6회로 조금 줄었다.
- 학습 속도: mem_on은 0.5M당 약 6.6분, mem_off는 약 5.4분.

## 5. 해석: 왜 기억이 강제되지 않았나

1. **헛도리가 싸다.** 헛도리 벌점 −0.02는 스텝 비용 10 decision분이다. 서빙 +3.0, 목표 +2.0에
   비하면 에피소드당 2~3회 떠보는 비용(약 −0.05)은 거의 없다. 정확히 기다리는 것과 몇 번 떠보는
   것의 차이가 학습 신호로 거의 드러나지 않는다.
2. **관측에 시계가 있다.** 에피소드 남은 시간(`TimeRemainingNormalized`)과 주문 남은 시간이
   관측에 들어 있다. 이 조건은 1접시 목표라 에피소드가 곧 요리 한 번이다. 숙련된 정책은 매번
   비슷한 경로로 냄비를 채우므로 채우는 시점이 에피소드 시작 기준으로 비슷할 것이다. 그러면
   "남은 시간이 얼마 이하면 뜬다"로 조리 완료를 대신 알 수 있다. memory 없이도 조리 진행을
   추정할 수 있는 셈이다. (가설이다. 채우는 시점의 분포는 측정하지 않았다.)
3. **RNN 쪽이 초반 탐색이 늦었다.** 같은 스텝 수에서 체인을 배우는 속도가 느렸다. 이 조건에서는
   그 비용을 상쇄할 만큼의 이득이 memory에서 나오지 않았다. (시드 하나라 편차가 섞여 있다.)

두 번째 이유 때문에 이 결과가 "기억이 필요 없는 과제"라는 뜻은 아니다. 여러 접시를 만드는
최종 난이도에서는 냄비를 채우는 시점이 에피소드마다 달라 시계로 대신하기 어렵다. 다만 그
조건은 무작위 초기화로 학습되지 않아서(v1) 이번 비교에서 쓸 수 없었다.

## 6. 한계

- **시드 하나씩이다.** 학습 속도 차이(첫 서빙 0.6M, 99% 도달 약 1.5M)에는 시드 편차가 섞여
  있다. 방향은 모든 구간에서 같지만, 크기는 믿을 수 없다.
- **쉬운 조건이다.** 1접시 목표, 레시피 1종, 손질 없음이다. 최종 난이도에서 memory 효과는
  확인하지 못했다.
- 헛도리 지표는 "덜 끓었을 때 뜬 횟수"만 센다. 조리 완료 후 얼마나 기다렸다가 떴는지(늦게 뜬
  낭비)는 세지 않는다. 다만 에피소드 길이가 그 낭비를 간접적으로 반영한다.
- 관측의 시계(§5의 2)를 가리는 조건은 돌리지 않았다.

## 7. 다음 단계 후보

기억을 실제로 강제하려면 아래 중 하나가 필요하다. 모두 보상·관측 설계 변경이라 별도 작업이다.

1. 헛도리 벌점을 키운다 (예: −0.02 → −0.2). 떠보기가 비싸지면 타이밍을 맞추는 쪽이 이득이 된다.
2. 관측에서 시계 역할을 하는 값(에피소드 남은 시간, 주문 남은 시간)을 빼거나 거칠게 만든 조건을
   추가해 비교한다.
3. 시드를 늘려(런당 2~3개) 학습 속도 차이의 크기를 확인한다.
